## Часть 1

Используя LLM (например, deepseek) и дополнительную техническую литературу, справочные сайты, выполнить анализ программного и информационного обеспечения сайта кафедры используя  ГОСТ 19.503-79, составить фрагмент руководства системного программиста, где описать раздел 2 этого руководства.

### 1. Общие сведения о программе

Документ описывает архитектуру и состав ПО информационного портала кафедры ИКТ РГПУ им. А. И. Герцена, расположенного по адресу ict.herzen.spb.ru.

В основе системы лежит плоскофайловая CMS Grav, запущенная в контейнерах Docker под управлением Kubernetes. Приложение выполняет функции публикации контента (новости, расписание, учебные материалы) и взаимодействует с внешними API Google (OAuth 2.0, Календарь, Диск). Сборка и доставка реализованы через GitLab CI/CD с использованием Kaniko, а готовые образы хранятся в корпоративном реестре registry-git.herzen.spb.ru. Веб-сервер — Nginx, серверная логика — PHP 7.x в среде Linux (Ubuntu).

### 2. Структура программы

Взаимодействие пользователя с системой организовано по модели клиент-сервер. Клиентом выступает веб-браузер, серверной частью — контейнеризированное приложение в Kubernetes. Схема прохождения запроса: браузер → Ingress-контроллер → Service apps-ict → Pod с контейнером.

| Компонент | Файл / Ресурс | Функциональное назначение |
|-----------|----------------|----------------------------|
| Система управления контентом Grav | `grav/user/` | Содержит весь пользовательский контент, темы оформления и расширения сайта кафедры |
| Контейнерный образ | `Dockerfile` | Формирует образ на базе `dmitriizolotov2/grav`, интегрируя пользовательские данные |
| Манифесты Kubernetes | `deploy.yaml` | Задают правила для Service, Ingress и Deployment в кластере |
| Процесс непрерывной доставки | `.gitlab-ci.yml` | Реализует три этапа: создание образа, развёртывание в кластере, удаление старых версий из реестра |
| Настройки веб-сервера | `.htaccess` | Определяет правила перенаправления (mod_rewrite), защиту от атак и ограничение доступа к каталогам |
| Авторизация Google | `oauth2callback.php` | Получает код авторизации и токен доступа для работы с API Google |
| Интеграция с Google Диском | `pr_gd_save_callback.php` | Обеспечивает выгрузку файлов из Диска, включая преобразование Google Docs в DOCX, XLSX или PDF |
| Настройка привязки GCA | `pr_gca_save_callback.php` | Сохраняет сопоставление страниц Grav с email-адресами в файл `gca.json` |
| Настройка привязки GDA | `pr_gda_save_callback.php` | Фиксирует соответствие между страницами Grav и идентификаторами папок Google Диска в файл `gda.json` |
| Данные для доступа к Google API | `client_id.json` | Хранит идентификатор клиента (`client_id`) и секретный ключ (`client_secret`) для проекта `spb-rgpu-ict-site-2018` |

**Связь между составными компонентами**

1. **Приём запроса**  
   Браузер пользователя отправляет HTTP-запрос на адрес `ict.herzen.spb.ru`. Запрос попадает на входной контроллер Kubernetes — **Ingress**.

2. **Маршрутизация внутри кластера**  
   Ingress передаёт запрос сервису **apps-ict** (порт 80), который, в свою очередь, направляет его в контейнер с работающим сайтом.

3. **Запуск обработки в Grav**  
   Ядро системы (Grav Core) открывает файл конфигурации `/user/config/system.yaml`, чтобы определить текущее оформление (активную тему — `ict`).

4. **Поиск страницы**  
   По адресу из запроса Grav находит нужный файл в папке `/user/pages/`.

5. **Обработка содержимого**  
   Плагины группы `markdown-*` преобразуют Markdown-текст в HTML.

6. **Вёрстка через шаблон**  
   Система применяет Twig-шаблон, расположенный в папке `/user/themes/ict/templates/`.

7. **Работа дополнительных плагинов**  
   При необходимости подключаются плагины (`login`, `form`, `events-manager` и другие).

8. **Отправка ответа**  
   Готовая HTML-страница возвращается пользователю в браузер.

**Связи с внешними программами**

| Внешняя система | Что используется | Зачем |
|----------------|------------------|--------|
| Google OAuth 2.0 | Протокол OAuth 2.0 | Для входа и получения прав доступа к данным Google |
| Google Calendar API | REST API через HTTPS | Чтобы получать события и расписание для сайта |
| Google Drive API | REST API через HTTPS | Чтобы скачивать файлы с Google Диска |
| GitLab Registry | Docker Registry API | Для хранения собранных образов |
| Kubernetes API | Управление через `kubectl` | Чтобы разворачивать приложение в кластере |
| GitLab CI | GitLab Runner и Kaniko | Для автоматической сборки и публикации образов |

### 3. Настройка программы

Настройка приложения выполняется на нескольких уровнях:

#### 3.1. Переменные окружения GitLab CI

В настройках проекта GitLab задаются переменные:
- `CI_REGISTRY`
- `CI_REGISTRY_USER`
- `CI_REGISTRY_PASSWORD`

Они используются для авторизации при сборке и загрузке Docker-образа в реестр.

#### 3.2. Конфигурация Kubernetes

- Файл `/config-production` (KUBECONFIG) должен находиться на узле, где запущен GitLab Runner, чтобы выполнять команды `kubectl`.
- Количество реплик приложения (по умолчанию — 1) задаётся в файле `deploy.yaml`.

#### 3.3. Учётные данные Google API

- Файл `client_id.json` необходимо поместить в папку `php_scripts/` внутри контейнера.
- Адрес для перенаправления (Redirect URI) должен соответствовать адресу сервера:  
  `http://<host>/oauth2callback.php`

#### 3.4. Настройка CMS Grav

- Все конфигурационные файлы находятся в каталоге `grav/user/config/`.
- Активная тема оформления указывается в файле `system.yaml`.

#### 3.5. Связь страниц с данными Google

Через административную панель Grav настраиваются соответствия:
- `gca.json` — привязка страницы сайта к адресу электронной почты.
- `gda.json` — привязка страницы сайта к идентификатору папки на Google Диске.

### 4. Проверка программы

Для проверки работоспособности системы применяются следующие методы:

#### 4.1. Проверка сборки Docker-образа

- Выполните коммит в ветку `master`.
- В GitLab CI стадия `build` должна завершиться без ошибок.

#### 4.2. Проверка развёртывания в Kubernetes

- После успешной сборки стадия `publish` применяет конфигурацию из файла `deploy.yaml`.
- Выполните команду:  
  `kubectl get pods -n default`  
  Pod должен находиться в статусе `Running`.

#### 4.3. Проверка доступности сайта

- Откройте в браузере адрес: `http://ict.herzen.spb.ru/`
- Убедитесь, что главная страница отображается корректно.

#### 4.4. Проверка авторизации Google OAuth

- Перейдите по адресу: `/oauth2callback.php`
- При правильной настройке произойдёт перенаправление на страницу входа в Google.

#### 4.5. Проверка загрузки файлов с Google Drive

- Отправьте запрос к скрипту `/pr_gd_save_callback.php`, передав параметры:  
  `id`, `type`, `filename`
- Браузер должен начать загрузку запрошенного файла.

### 6. Сообщения системному программисту

| Сообщение / Ситуация | Причина | Действие |
|----------------------|---------|----------|
| Pod в статусе `CrashLoopBackOff` | Ошибка в PHP-коде или отсутствует файл `client_id.json` | Посмотреть логи: `kubectl logs <pod-name>`; проверить, что Dockerfile копирует все необходимые файлы |
| `ImagePullBackOff` | Неправильные учётные данные для доступа к реестру или образ отсутствует | Проверить секрет: `kubectl get secret regsecret`; при необходимости создать заново |
| Ошибка HTTP 403 при запросе файлов | Правила из `.htaccess` блокируют доступ | Проверить директивы RewriteRule; убедиться, что модуль mod_rewrite включён |
| Google API возвращает `invalid_client` | Неверно указан `client_id` или `client_secret` | Создать нового OAuth-клиента в Google Cloud Console и обновить файл `client_id.json` |
| Ошибка Google API: `Token has been expired` | Истёк срок действия refresh_token или повреждён файл `refresh.txt` | Удалить `json.txt` и `refresh.txt`; повторно пройти авторизацию через `/oauth2callback.php` |
| Стадия `cleanup` не выполняется (очистка реестра) | Устаревшие учётные данные в файле `.gitlab-ci.yml` | Обновить пароль пользователя `cleaner` в секции `cleanup` |
